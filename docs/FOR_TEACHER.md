# Инструкция для преподавателя: как завести задачу на базе шаблона

## 0. Подготовка курса (один раз)

1. Положите шаблон в отдельный репозиторий курса (например
   `net-course/hw-template`) и включите _Settings → General → Template
   repository_ — тогда у задачи появится кнопка _Use this template_.
2. В `.github/CODEOWNERS` замените `@your-org/teachers` на вашего
   пользователя или команду.
3. Настройте branch protection для `main` (см. README, раздел «Настройка
   репозитория на GitHub»). Эти настройки копируются вместе с репозиторием
   GitHub при создании задач из шаблона, но статус-чек-чеки лучше перепроверить
   в каждом репозитории задачи: имена джоб появляются после первого запуска CI.
4. Создайте команду студентов с правом Write на репозиториях задач или
   добавляйте студентов как collaborators.

## 1. Создание задачи

```bash
# через GitHub UI: Use this template -> Create repository -> hw01-ethernet
git clone git@github.com:<org>/hw01-ethernet.git && cd hw01-ethernet
```

## 2. Интерфейс (include/)

Опишите **только контракт**, без реализации. Реализация задания — на чистом C,
C++ оставьте тестам (GTest):

- **структуры с полями**: `eth_mac_t` (6 октетов), `eth_vlan_tag_t`
  (`tpid`, `pcp`, `dei`, `vid`), `eth_frame_t` (`dst`, `src`,
  `vlan_present`, `vlan`, `ether_type`, `length_field`, `payload`,
  `payload_len`);
- **методы**: `eth_frame_parse()` — разбор сырых байт в `eth_frame_t`;
  `eth_frame_serialize()` — запись кадра в буфер вызывающего кода;
- константы размеров (`ETH_ADDR_LEN`, `ETH_HEADER_LEN`,
  `ETH_VLAN_HEADER_LEN`, `ETH_MIN_PAYLOAD`, `ETH_MAX_PAYLOAD`,
  `ETH_FRAME_MIN_LEN`, `ETH_FRAME_MAX_LEN`) и EtherType/TPID
  (`ETH_TYPE_IPV4`, `ETH_TYPE_ARP`, `ETH_TYPE_IPV6`, `ETH_TYPE_VLAN`,
  `ETH_TYPE_QINQ`, `ETH_TYPE_MIN`), чтобы тесты и студент не дублировали
  «магические» числа;
- в комментариях укажите стандарты и RFC: **RFC 894** (IPv4 over Ethernet,
  полезная нагрузка 46..1500), **RFC 7042** (реестр EtherType),
  **RFC 826** (ARP), **RFC 2464** (IPv6 over Ethernet), **IEEE 802.3**
  (кадр, поле длины), **IEEE 802.1Q / 802.1ad** (VLAN/QinQ);
- типы — стандартные (`stdbool.h`/`stdint.h`/`stddef.h`), заголовок
  самодостаточный, с `extern "C"`-обёрткой (чтобы тесты на C++ линковались
  без сюрпризов);
- если в задаче есть внешняя зависимость (сеть, время, ФС), оформите её как
  таблицу функций (vtable) + `ctx` — тесты подставят fake вместо реального
  кода.

Требования к комментариям: каждый реализуемый символ должен иметь контракт —
что принимает, что возвращает, что считается ошибкой, кто владеет памятью.
Пометьте их `TODO(student)`. Студент **не имеет права** менять заголовки;
CI проверит.

В текущем примере важно явно оговорить:

- вход API — кадр **без преамбулы/SFD и без FCS**;
- многобайтовые поля — в сетевом порядке байт (big-endian);
- `payload` после разбора указывает внутрь входного буфера (структура не
  владеет памятью);
- поддерживается ровно один VLAN-тег, вложенные QinQ отвергаются;
- при ошибке выходной объект не изменяется.

## 3. Заглушки (src/)

Оставьте скелет без логики **на C** (`*.c`): тела возвращают код ошибки
(`-1`, `NULL` и т.п.), параметры заглушены `(void)param;`. Это даёт
собирающийся проект с падающими тестами — студент сразу видит и контракт,
и критерий готовности.

## 4. Тесты (tests/)

Пишите на GTest в `tests/test_<unit>.cpp` (C++ нужен только здесь — свой
CHECK/ASSERT писать не придётся), не забыв добавить файл в
`add_executable(hw_tests ...)` в `CMakeLists.txt`. Подключайте C-заголовки
через `extern "C"`. Рекомендации:

- обязательно покройте **оба вида трафика**: нетэгированный (Ethernet II) и
  тегированный (IEEE 802.1Q, TPID `0x8100`) — отдельными тестами;
- проверяйте точную раскладку байт на проводе и round-trip
  serialize → parse → сравнение полей;
- покрывайте граничные значения: PCP `0..7`, DEI `0/1`, VID `0/1/4095`,
  полезную нагрузку ровно `ETH_MIN_PAYLOAD` и `ETH_MAX_PAYLOAD`;
- проверяйте ошибки: кадр короче заголовка, обрезанный VLAN-тег, нагрузка
  меньше 46 или больше 1500 байт, вложенные теги, неверные `tpid`/`pcp`/`vid`
  при сериализации, слишком маленький буфер, `NULL`-аргументы и неизменность
  выходного объекта при ошибке;
- если контракт предполагает владение памятью, добавьте тест, в котором
  студент обязан её освободить: ASan с `detect_leaks=1` это проверит (в
  текущем примере структура памятью не владеет);
- число и имена тестов вынесите в условие задачи — так студент знает критерий.

## 5. Сборка

Если студенту разрешены дополнительные файлы — добавьте их (`.c`) в
`add_library(hw ...)` заранее (файл защищён CI, студент дописать его не сможет).
Обновите `docs/FOR_STUDENT.md`, если нужно что-то специфичное для задачи.

## 6. Проверка шаблона перед выдачей

```bash
cmake --preset debug && cmake --build --preset debug
ctest --preset debug        # ожидаемо: все тесты красные на заглушках
cmake --preset asan && cmake --build --preset asan && ctest --preset asan
```

Затем — на отдельной ветке — напишите эталонное решение и убедитесь, что все
тесты зелёные (в том числе под санитайзерами). После проверки эталонную ветку
удалите или спрячьте: студент не должен её видеть.

## 7. Выдача и приёмка

- Раздайте ссылку на репозиторий задачи, дедлайн и правило сдачи: **MR из
  ветки `solution` в `main`**, слитый с зелёным пайплайном.
- Имена веток и MR удобнее стандартизировать: `solution`, `hw01-<ник>`.
- На этапе приёмки смотрите пайплайн MR (время выполнения, sanitizer-логи) и
  оставляйте комментарии в диффе. Merge доступен только при зелёном CI
  (и, если включён Require review from Code Owners, после вашего approve).
