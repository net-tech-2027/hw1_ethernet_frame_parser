# Шаблон домашнего задания по сетевым технологиям (C)

Готовый каркас репозитория для домашек: **преподаватель** описывает интерфейс,
тесты и ограничения; **студент** реализует логику в `src/` **на чистом C**,
проверяет решение локально через **ctest**, а merge его MR в GitHub возможен
**только** при успешном прохождении всего CI-пайплайна (сборка, тесты,
ASan+UBSan, проверка защищённых файлов).

**C++ в шаблоне используется только внутри тестов** — как готовый фреймворк
GoogleTest (ASSERT/EXPECT, фикстуры), чтобы не писать свою реализацию CHECK,
ASSERT и т.д. Весь код, который пишет и сдаёт студент, — на C.

## Пример задачи в шаблоне

`include/ethernet.h` описывает разбор и сериализацию Ethernet-кадра по
общепринятому стандарту:

- **Ethernet II** — MAC-адреса, EtherType, полезная нагрузка. EtherType IPv4
  (`0x0800`) и ограничение нагрузки 46..1500 байт определены в **RFC 894**;
  реестр EtherType — **RFC 7042**; ARP — **RFC 826**; IPv6 over Ethernet —
  **RFC 2464**.
- **IEEE 802.3** — если поле типа меньше `0x0600`, это длина полезной
  нагрузки, а не EtherType (выставляется `length_field`).
- **IEEE 802.1Q / 802.1ad (VLAN)** — тег 4 байта между MAC-адресами и
  EtherType: TPID `0x8100`/`0x88A8`, TCI с полями PCP (3 бита), DEI (1 бит) и
  VID (12 бит).

Интерфейс содержит структуры с полями и методы:

- `eth_mac_t` — MAC-адрес (6 октетов);
- `eth_vlan_tag_t` — разобранный VLAN-тег (`tpid`, `pcp`, `dei`, `vid`);
- `eth_frame_t` — кадр (`dst`, `src`, `vlan_present`, `vlan`, `ether_type`,
  `length_field`, `payload`, `payload_len`).

Студент реализует две функции:

- `eth_frame_parse()` — разбирает сырые байты в `eth_frame_t`; `payload`
  указывает внутрь входного буфера, поддерживается ровно один VLAN-тег,
  некорректные длины и вложенные теги QinQ отвергаются; при ошибке `*out`
  не изменяется.
- `eth_frame_serialize()` — записывает кадр в буфер вызывающего кода
  (tagged или untagged), возвращает число байт или `-1`; проверяет поля
  VLAN, диапазон нагрузки и размер буфера.

FCS (CRC-32) в API не входит: сетевой адаптер обычно отбрасывает её сам.
Все многобайтовые поля — в сетевом порядке байт (big-endian).

Тесты в `tests/test_ethernet.cpp` — на C++ с GTest. В них есть **отдельные
прогоны тегированного и нетэгированного трафика**: точные байты на проводе,
round-trip parse → serialize, разбор PCP/DEI/VID, границы MTU, слишком
короткие и слишком длинные кадры, вложенные теги, `NULL`-аргументы и
неизменность выходного объекта при ошибке.

## Что проверяет CI (3 джобы, все обязательны для merge)

| Джоба                       | Что делает                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protected files untouched` | Сравнивает MR с базовой веткой и **падает**, если изменены `include/`, `tests/`, `docs/`, `CMakeLists.txt`, `CMakePresets.json`, `.github/`, `README.md` |
| `build & ctest`             | Сборка и прогон всех тестов через `ctest` на **gcc** и **clang**                                                                                         |
| `ASan + UBSan`              | Сборка с `-fsanitize=address,undefined -fno-sanitize-recover=all` и прогон тестов (в т.ч. с `detect_leaks=1`)                                            |

MR с любым красным шагом слить нельзя (правила ветки настраиваются один раз —
см. «Настройка репозитория на GitHub» ниже).

## Пайплайн действий преподавателя

Подробная инструкция с примерами: [docs/FOR_TEACHER.md](docs/FOR_TEACHER.md). Кратко:

1. **Завести репозиторий задачи.** Нажать _Use this template_ (или скопировать
   репозиторий) → новый репозиторий вида `hw01-ethernet`.
2. **Описать интерфейс на C.** В `include/` создать/изменить заголовки:
   структуры кадра и VLAN-тега, константы и функции
   `eth_frame_parse()`/`eth_frame_serialize()`, которые студент будет
   реализовывать. Контракт и сложность — в комментариях `TODO(student)`.
3. **Оставить заглушки.** В `src/` — скелет без логики, возвращающий код ошибки
   (сборка проходит, тесты падают — так и задумано).
4. **Написать тесты в `tests/`** на GTest (C++ только здесь): тегированный и
   нетэгированный трафик, точная раскладка байт, round-trip, границы MTU,
   ошибки формата и `NULL`-аргументы — студенту разрешено их читать, но не
   менять. Количество тестов вписать в условие задачи, чтобы студент понимал
   критерий готовности.
5. **Настроить ограничения** (один раз на курс):
   - branch protection на `main`: обязательный PR, обязательные проверки
     `protected files untouched`, `build & ctest (…gcc/g++)`,
     `build & ctest (…clang/clang++)`, `ASan + UBSan`, «branch must be
     up-to-date before merging»;
   - в `.github/CODEOWNERS` заменить `@your-org/teachers` на себя/команду.
6. **Выдать задачу**: раздать ссылку/доступ, дедлайн, критерии; эталонное
   решение держать вне репо или в приватной ветке.

## Пайплайн действий студента

Подробная инструкция: [docs/FOR_STUDENT.md](docs/FOR_STUDENT.md). Кратко:

1. **Склонировать** репозиторий задачи и собрать локально:
   ```bash
   git clone <репозиторий задачи> && cd hw01-ethernet
   cmake --preset debug          # первый configure скачает GTest (FetchContent)
   cmake --build --preset debug
   ctest --preset debug          # заглушки красные — это норма, см. TODO(student)
   ```
2. **Прочитать контракт**: комментарии `TODO(student)` в `include/ethernet.h`
   и тесты в `tests/` — точное ожидаемое поведение.
3. **Реализовать** логику **только в `src/`, на C**. Список файлов сборки в
   `CMakeLists.txt` защищён: если преподаватель разрешил отдельные файлы,
   он сам добавляет их в список источников заранее (в текущем примере
   реализация кладётся в `src/ethernet.c`).
4. **Проверить локально** обе конфигурации:
   ```bash
   ctest --preset debug
   cmake --preset asan && cmake --build --preset asan && ctest --preset asan
   ```
5. **Запушить ветку и открыть MR** в `main`. CI проверит всё автоматически;
   шаблон MR содержит чек-лист.
6. **Довести до зелёного**: исправить замечания компиляторов, тестов и
   санитайзеров; после всех зелёных проверок MR сливается (если настроен
   CODEOWNERS — потребуется approve преподавателя).

## Локальный запуск тестов (ctest)

| Действие               | Команда                                                                     |
| ---------------------- | --------------------------------------------------------------------------- |
| Конфигурация           | `cmake --preset debug`                                                      |
| Сборка                 | `cmake --build --preset debug`                                              |
| Все тесты              | `ctest --preset debug`                                                      |
| Один тест по имени     | `ctest --preset debug -R EthernetFrameTest`                                 |
| Санитайзеры (как в CI) | `cmake --preset asan && cmake --build --preset asan && ctest --preset asan` |

## Настройка репозитория на GitHub (один раз на курс или на задачу)

1. _Settings → Collaborators and teams_: выдать студентам права **Write**.
2. _Settings → Branches → Add branch ruleset_ (или _Add rule_) для `main`:
   - Require a pull request before merging;
   - Require status checks to pass: `protected files untouched`,
     `build & ctest (g++)`, `build & ctest (clang++)`, `ASan + UBSan`
     (имена появятся после первого запуска CI);
   - Require branches to be up to date before merging;
   - (опционально) Require review from Code Owners — тогда нужен approve
     преподавателя.
3. Проверить, что в `.github/CODEOWNERS` указаны реальные логины/команды.
4. В настройках Actions ничего дополнительно включать не нужно: workflow
   запускается на push в `main` и на все pull request.

## Требования к окружению

- CMake **≥ 3.21**, компилятор gcc ≥ 10 или clang ≥ 12 (реализация на C11;
  C++17 нужен только для сборки тестов на GTest).
- Git; при первом `cmake --preset debug` нужен доступ к сети для скачивания
  GTest (FetchContent). Офлайн-вариант: установить пакет `libgtest-dev`
  (`GTest ≥ 1.14`) — CMake подхватит системный GTest автоматически.
- Работает на Linux/macOS/WSL; для Windows — MSVC не входит в CI, сдача
  выполняется через GitHub.
